# 08 非功能需求与技术亮点

## 1. 非功能需求

## 1.1 性能目标
- 首页文章列表接口：P95 < 300ms（缓存命中后）
- 文章详情接口：P95 < 200ms（缓存命中后）
- 搜索接口：P95 < 500ms
- 发布文章接口：主请求不等待索引同步与通知发送

## 1.2 可用性目标
- Kafka 消费失败可重试
- ES 同步失败可补偿
- Redis 故障时允许回源数据库
- 非关键异步链路失败不能影响主业务写入

## 1.3 安全要求
- JWT 鉴权
- 后台接口 RBAC
- 参数校验
- XSS 过滤
- 登录限流
- 评论防刷
- 图片上传类型限制

## 1.4 可维护性要求
- 模块化目录
- 统一日志格式
- 统一异常处理
- 统一错误码
- 接口与表结构文档齐全

## 2. 可以重点展示的技术亮点

## 2.1 文章发布的异步解耦
**亮点描述：**
文章发布主事务只处理 MySQL 持久化，后续索引同步、关注通知、热榜刷新由 Kafka 异步驱动，提升主链路响应速度并降低耦合。

**面试价值：**
可以展开讲事务边界、消息投递、一致性与重试。

---

## 2.2 Elasticsearch 全文检索
**亮点描述：**
支持标题、摘要、正文、标签多字段检索，高亮展示，分类标签过滤，最新/最热排序。

**面试价值：**
可以讲 mapping、分词器、权重、聚合、高亮、索引重建。

---

## 2.3 Redis 热点缓存与计数器
**亮点描述：**
文章详情、热门文章、分页列表走 Redis 缓存；阅读量通过 Redis 原子计数，再定期落库。

**面试价值：**
可以讲缓存 key 设计、TTL、缓存一致性、击穿/穿透/雪崩处理。

---

## 2.4 Outbox Pattern（增强项）
**亮点描述：**
将业务更新与事件记录写在一个数据库事务中，再由后台任务可靠投递到 Kafka，避免事务成功但消息发送失败的问题。

**面试价值：**
这是典型的“知道生产级一致性问题”的信号。

---

## 2.5 幂等消费
**亮点描述：**
消息消费端基于 `message_key + consumer_group` 做幂等，防止重复创建索引、重复发通知、重复统计。

**面试价值：**
能体现你不只会发消息，也考虑了重复消费问题。

---

## 2.6 热榜与时间衰减
**亮点描述：**
基于浏览、点赞、评论、收藏计算热度分，并加入时间衰减，让新内容有机会进入热榜。

**面试价值：**
可以讲推荐/排序的工程实现，而不是纯 CRUD。

---

## 2.7 JVM 与线程池观测
**亮点描述：**
对文章详情、搜索、批量重建索引等操作进行 GC、线程池、堆内存、接口耗时监控。

**面试价值：**
可以讲你如何通过 JFR、GC 日志、jstack 观察性能问题。

---

## 3. 不建议硬秀的点

以下点如果没有真实业务压力，不建议在第一阶段强做：

- 全量微服务拆分
- 所有模块都用 Dubbo
- 文章编辑锁用本地读写锁控制分布式并发
- 用 BlockingQueue 替代评论主写路径
- 为网关直接上 ZGC/Shenandoah
- 用 ConcurrentHashMap 做用户基础信息主缓存

这些点容易被问穿。

## 4. 压测建议

## 4.1 压测场景
- 首页文章列表
- 文章详情（缓存命中）
- 文章详情（缓存未命中）
- 搜索接口
- 发布文章接口
- 评论接口

## 4.2 观测指标
- QPS
- 平均响应时间
- P95/P99
- Redis 命中率
- Kafka 堆积
- GC 次数
- Full GC 次数
- 线程池活跃线程数

## 4.3 压测工具
- JMeter
- k6
- wrk（适合接口压测）

---

## 5. 可观测性要求

至少暴露：
- `/actuator/health`
- `/actuator/metrics`
- `/actuator/prometheus`

### 建议接入指标
- `http.server.requests`
- JVM heap
- GC pause
- Kafka consumer lag
- 自定义线程池指标
- Redis 调用耗时

## 7. 最终展示话术建议

这个项目最好的展示方式不是“用了很多组件”，而是：

> 围绕博客发布链路、热点读取链路和全文搜索链路，设计了缓存、消息驱动、全文检索和统计体系，并通过 JVM 观测与压测验证性能改进效果。

这句话比“我用了 Redis/Kafka/ES/Dubbo/K8s”更有说服力。
