# 09 Cursor 协作规则

这份文件是给 Cursor 的核心行为约束。

## 1. 总原则

Cursor 必须严格以本项目指导包为准进行开发，不允许擅自重构业务边界、随意修改表结构、胡乱新增中间件。

---

## 2. 代码生成规则

1. 优先输出**完整文件**
2. 不要只给代码片段
3. 每次只实现一个明确模块或闭环
4. 不要同时改太多模块
5. 改动前先说明影响范围
6. 所有新增文件都要给路径

---

## 3. 架构规则

1. 第一阶段按模块化单体实现
2. 不允许一开始强拆微服务
3. Kafka 仅用于异步副作用链路
4. Elasticsearch 仅用于搜索
5. Redis 用于缓存、计数器、限流、登录态辅助
6. Dubbo 不是第一阶段必需

---

## 4. 数据库规则

1. 表前缀统一使用 `pb_`
2. 所有表都要有审计字段和逻辑删除字段
3. 文章元数据与正文分表
4. 出参禁止直接暴露数据库实体
5. 新增表/字段必须同时更新 SQL 文档
6. 复杂查询优先优化索引，不要堆业务代码绕开数据库设计

---

## 5. 后端编码规则

1. Controller 只做参数接收和响应返回
2. 业务逻辑放 Service / Manager
3. 复杂跨中间件逻辑放 Manager
4. 基础 CRUD 用 MyBatis-Plus
5. 复杂分页/聚合查询可用 XML
6. 参数校验必须使用 Validation
7. 返回结构统一为 `ApiResponse<T>`
8. 统一错误码
9. 统一异常处理
10. 写接口要考虑事务边界

---

## 6. 安全规则

1. 登录使用 JWT
2. 后台接口必须做权限校验
3. 评论与登录接口要有频率限制
4. 所有写接口必须校验当前用户身份
5. 上传接口必须限制文件类型和大小

---

## 7. 缓存规则

1. 查询先查缓存，未命中再回源
2. 更新文章后必须删除相关缓存
3. 列表缓存建议短 TTL
4. 详情缓存建议单独 key
5. 计数器走 Redis 原子操作
6. 不要把 Redis 当成主存储

---

## 8. 消息规则

1. Kafka 事件必须定义明确的事件类型
2. 事件体必须包含业务主键与必要元数据
3. 消费端必须考虑幂等
4. 消费失败要记录日志与重试
5. 不能因为消息失败回滚已经成功的主事务
6. 第二阶段可以引入 Outbox

---

## 9. 搜索规则

1. 只同步已发布文章到 ES
2. 删除/下线文章时索引必须同步处理
3. 搜索结果要支持高亮
4. 支持分类/标签过滤
5. 提供重建索引能力

---

## 10. 前端规则

1. 门户端和管理台分开实现
2. API 封装统一管理
3. 登录态统一保存在 Pinia
4. 路由权限要区分前台和后台
5. 页面先保证功能，再优化样式
6. 表单校验要完整

---

## 11. 输出格式规则

每次让 Cursor 开发一个模块时，必须要求其输出以下内容：

### 11.1 改动说明
- 本次实现了什么
- 涉及哪些文件
- 数据库是否变更

### 11.2 代码输出
- 给完整文件内容
- 给文件路径

### 11.3 验证说明
- 如何启动
- 如何测试接口
- 如何验证前端页面

### 11.4 下一步建议
- 接下来适合做什么模块

---

## 12. 禁止事项

Cursor 不允许：

- 为了省事把所有逻辑写到一个 ServiceImpl
- 随意删除已有文档要求
- 不说明原因就改表结构
- 在第一阶段擅自拆成多个微服务
- 一次性生成上万行无法审阅的代码
- 忽略幂等、缓存一致性和权限控制

---

## 13. 你给 Cursor 的固定开场白建议

你每次都可以先贴这一段给 Cursor：

> 请严格按照项目指导文件开发，不要擅自修改架构边界、表结构命名和接口规范。一次只实现一个完整小闭环，输出完整文件路径、代码内容、数据库变更、验证步骤和下一步建议。
