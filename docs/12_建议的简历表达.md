# 12 简历表达建议

## 1. 项目一句话描述

> 基于 Spring Boot 3、MySQL、Redis 与 Spring 进程内事件驱动的模块化单体博客平台，围绕文章发布链路、全文搜索链路、热点读取链路和目录树导航链路，展示缓存一致性与可观测能力。

## 2. 可写进简历的要点

- 设计并实现文章发布、评论互动、站内通知、点赞收藏、热榜统计等完整业务闭环
- 基于 Redis 实现文章详情缓存、PV/UV 计数、热度 ZSet 排序，优化热点读取场景性能
- 基于 Spring `ApplicationEventPublisher` 解耦文章发布后的通知生成与热度累加
- 基于 MySQL `LIKE` 多表 JOIN 实现标题 / 摘要 / 正文 / 标签的全文检索与服务端高亮
- 设计 MySQL + Redis 的最终一致性方案（Cache Aside + 事件驱动缓存失效）
- 设计并实现目录树模块（物化路径 + 叶子校验 + 文章计数一致性），打通「分类 vs 目录树」双维度导航
- 通过统一异常 / 统一响应 / Logback 滚动日志完成工程化基础
- 前端 Element Plus 从全量注册改为按需引入，主包体积减少约 85%

- ✅ "Redis 提供缓存 + 计数器 + 热度 ZSet，搜索基于 MySQL `LIKE` 多表 JOIN + 服务端转义高亮，所有中间件都有真实业务支撑"
- ✅ "鉴权走自定义 JwtAuthenticationFilter + ThreadLocal 而非 Spring Security 过滤器链，是因为当前需求简单、自定义更直观"
- ✅ "目录树作为「知识图谱维度」与分类并存：文章必须挂到叶子节点才能保存，计数一致性由 service 层维护"
- ✅ "项目重点不是组件数量，而是缓存一致性与可观测"

## 5. 常被问到的问题与回答方向

### Q1: 为什么用 Spring 进程内事件而不是 Kafka？
A: 单仓单进程阶段，进程内事件足够支撑业务解耦；引入 Kafka 会增加运维成本（Broker、Zookeeper、副本、监控）。当前实现可以在不改动业务的前提下，替换为 Redis Stream 或 Kafka Outbox。

### Q2: Redis 缓存如何与 MySQL 保持一致？
A: 写完事务后删除详情缓存（Cache Aside）。对强实时性要求不高的列表，采用 DB + 短 TTL。计数器走 Redis 原子命令，不强制立即同步到 MySQL。

### Q3: 为什么不用 Elasticsearch 做搜索？
A: 个人博客数据量小（万级以下），`LIKE %keyword%` 前缀通配完全够用；引入 ES 要多一个常驻 512MB+ 的容器、索引同步一致性、冷启动慢等成本，收益不成正比。当前搜索走 MySQL 多表 JOIN（标题/摘要/正文/标签四字段），服务端做 HTML 转义 + 高亮。数据量上去后，升级路径是 MySQL `FULLTEXT`（ngram 分词器）或重新引入搜索引擎。注意：**项目早期确实用过 ES 做过索引同步（已下线）**，这段经历可以讲，但要说清楚下线原因（成本 > 收益）。

### Q4: 为什么要自定义 JwtAuthenticationFilter 而不是用 Spring Security？
A: 当前项目鉴权需求简单（JWT + 拦截白名单），自定义过滤器更直观且代码量更少。Spring Security 仍保留做 CSRF / CORS 配置 + 过滤器链挂载。

### Q5: 目录树和分类有什么区别？
A: 分类是「文章归类」（每篇文章一个分类 ID），目录树是「知识图谱维度」（文章必须挂到某个叶子节点）。两者并存互不冲突。目录树用物化路径 + 叶子校验保证挂载点合法，service 层维护计数一致性。

### Q6: 热度怎么算？
A: 实时通过浏览 +1、点赞 +10 累加 Redis ZSet score。每 5 分钟从 MySQL 全量刷新兜底。接口 `/api/stats/hot` 返回前 N。

### Q7: 鉴权怎么防 Token 泄露？
A: 双 Token 机制（accessToken 24h + refreshToken 7d）；refreshToken 存 Redis 可主动失效；accessToken 退出时进 Redis 黑名单。黑名单 TTL 与 accessToken 剩余有效期一致。

> - 提供 Docker Compose 一键启动（MySQL + Redis + JDK17/Maven），`scripts/start-all.bat` 5 分钟内拉起完整环境
