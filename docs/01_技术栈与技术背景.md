# 01 技术栈与技术背景

## 1. 总体原则

技术选型要同时满足两件事：

1. 能支撑业务场景
2. 能体现工程表达力

本项目采用「核心必需 + 展示增强 + 可演进扩展」三层技术栈设计。

---

## 2. 后端核心技术栈

### 2.1 Java 17
**用途**：主开发语言，使用 record、var、文本块等现代特性。

**理由**：LTS 版本，Spring Boot 3.x 原生适配。

### 2.2 Spring Boot 3.2.5
**用途**：Web、IOC、AOP、事务、配置管理、整合中间件。

**理由**：开发效率高，生态成熟。

### 2.3 Spring MVC
**用途**：REST API 暴露，统一 `/api/**` 前缀。

### 2.4 Spring Validation
**用途**：参数校验（`@Valid` + `@RequestBody`）。

### 2.5 Spring Security（仅做配置壳 + CORS/CSRF）
**用途**：在 `SecurityConfig` 中关闭 CSRF、配置 CORS、设置 Session 为 STATELESS，并把 `JwtAuthenticationFilter` 加到过滤器链中。

**注意**：鉴权的「拦截与放行白名单」由 `JwtAuthenticationFilter.shouldNotFilter` 决定，不是 Spring Security 的 `authorizeHttpRequests`。`authorizeHttpRequests` 当前是 `anyRequest().permitAll()` —— 真正的权限校验在业务代码（`LoginUserHolder.get().isAdmin()`）内做。

### 2.6 JWT（jjwt 0.12.6）
**用途**：登录后颁发 `accessToken` + `refreshToken`。

**流程**：
- `AuthService.login` 颁发 token，refreshToken 存 Redis
- `JwtAuthenticationFilter` 解析 accessToken，还原 `LoginUser` 写入 `LoginUserHolder`（ThreadLocal）
- `AuthService.logout` 把 accessToken 写入 Redis 黑名单
- `AuthService.refreshToken` 用 refreshToken 换新 accessToken

### 2.7 MyBatis-Plus 3.5.11
**用途**：基础 CRUD、条件构造器、分页、逻辑删除。

**理由**：复杂查询仍可用 XML 精细控制。

## 3. 数据存储与中间件

### 3.1 MySQL 8.0
**承接内容**：用户、文章元数据、文章正文、评论、点赞、收藏、关注、通知、登录日志、文章日统计、文件、系统配置、目录树主表、目录树节点。

**理由**：典型事务场景，易于建模与索引优化。

### 3.2 Redis 7.x
**承接内容**：
- 文章详情缓存（`pureblog:article:detail:{id}`，TTL 30 分钟）
- 热门文章 ZSet（`pureblog:article:hot:zset`）
- PV 计数器（`pureblog:article:pv:{id}`，TTL 2 天）
- UV 集合（`pureblog:article:uv:{id}:{date}`，TTL 2 天）
- 用户资料缓存（`pureblog:user:info:{id}`，TTL 30 分钟）
- 验证码（`pureblog:captcha:{key}`，TTL 5 分钟）
- 刷新 Token（`pureblog:refresh:token:{userId}`）
- Token 黑名单（`pureblog:token:blacklist:{token}`）

**理由**：博客是读多写少系统，Redis 收益明显。

### 3.3 全文搜索（MySQL LIKE）
**承接内容**：文章检索，匹配标题 / 摘要 / 正文 / 标签名四个字段，只返回 `status=PUBLISHED` 的文章。

**实现要点**：
- 单条 SQL 完成多表 JOIN（`pb_article` ⋈ `pb_article_content` ⋈ `pb_article_tag` ⋈ `pb_tag`），手写 `LIMIT/OFFSET` 分页
- LIKE 通配符按字面量处理（`ESCAPE '!'`），避免用户搜 `100%` 命中任意内容
- 高亮在服务端完成：**先把原文 HTML 转义，再插入 `<em>` 标签**（前端用 `v-html` 渲染，不转义会导致 XSS）
- 正文片段截取 ±75 字符，每篇文章最多 3 条，与原 ES 版 `fragmentSize=150` / `numberOfFragments=3` 对齐

**为什么不用 Elasticsearch**：个人博客数据量小（万级以下），`LIKE` 完全够用；ES 带来 512MB+ 常驻内存、独立容器、索引同步一致性、冷启动慢等成本，收益不成正比。数据量上去后的升级路径：MySQL `FULLTEXT` + ngram 分词器，或重引搜索引擎。

### 3.4 异步事件（Spring 进程内）
**事件类型**（在 `pureblog-common` 的 `event/` 包下）：

| 事件 | 发布方 | 监听方 |
| --- | --- | --- |
| `CommentCreatedEvent` | `CommentServiceImpl` | `NotificationEventListener` |
| `FollowCreatedEvent` | `UserServiceImpl` | `NotificationEventListener` |
| `StatsLikeArticleEvent` | `CommentServiceImpl` | `NotificationEventListener`、`StatsEventListener` |
| `StatsPvEvent` | `ArticleCacheManager` | `StatsEventListener` |

**为什么不用 Kafka**：
- 单体阶段进程内事件已经够用
- 避免运维额外中间件
- 后续可平滑替换为 Kafka 或 Redis Stream（详见 `docs/02` 第 8 节）

## 4. 前端技术栈

### 4.1 Vue 3 + TypeScript
两个独立项目：
- `frontend/pureblog-portal` —— 门户站点
- `frontend/pureblog-admin-web` —— 管理后台（按需启用）

### 4.2 Vite
构建与开发服务器。

### 4.3 Pinia
状态管理（`stores/user.ts`）。

### 4.4 Vue Router
路由守卫。门户根路径 `/`，管理后台根路径 `/admin`。

### 4.5 Element Plus
管理后台组件库。门户主要使用自写 CSS + Day.js。

### 4.6 Day.js
时间格式化（如 `relativeTime`）。

## 5. 文件与运维

### 5.1 配置文件
- `application.yml` —— 生产配置（连接 `mysql`、`redis` 容器名）
- `application-dev.yml` —— 本地开发配置（MySQL 走宿主机 `127.0.0.1:13306`）

### 5.2 Docker
- 根目录 `docker-compose.yml` —— MySQL + Redis + JDK17/Maven 构建容器（唯一入口，不再有 `deploy/` 下的 compose 文件）
- 一键启动：`scripts\start-all.bat`；一键停止：`scripts\stop-all.bat`

### 5.3 日志
- `logback-spring.xml` 配置：
  - 控制台 + 普通文件 + Error 单独文件
  - 按日期与大小滚动（100MB）
  - 保留 30 天

## 7. 并发与异步

### 7.1 `@EnableAsync`
在 `PureBlogApplication` 启用。

### 7.2 `ThreadPoolTaskExecutor`
在 `AppConfig` 中定义：
- 核心线程 8，最大 16
- 队列容量 200
- 拒绝策略：`CallerRunsPolicy`
- 线程名前缀：`pb-async-`

### 7.3 `@EventListener` + `@Async`
搜索同步、通知生成、统计累加等副作用都在监听器中处理，建议显式标注 `@Async` 以避免阻塞主流程。

---

## 8. 关于 Dubbo / 微服务 / Kafka

**当前阶段都不引入**。本项目核心展示的不是「用了多少组件」，而是：

- 我知道哪些技术值得用
- 我知道为什么用
- 我知道什么时候不滥用
- 我能把业务闭环、工程实现、性能治理讲清楚

后续如果需要演进：
- 将 `pureblog-notification` 拆为独立服务
- 将事件发布方（`CommentServiceImpl` 等）替换为 Kafka Producer
- 此时再考虑 Dubbo 是否必要

变更时需同步更新 `docs/00` 第 7~8 节、`docs/02` 第 8 节、`docs/09` 第 12 节。
