# 02 系统架构设计

## 1. 架构目标

本项目架构设计目标不是极端追求“服务越多越好”，而是：

- 先保证业务闭环可落地
- 再通过事件驱动展示中间件能力
- 最后预留服务化拆分空间

因此推荐采用：

> **模块化单体 + 异步事件驱动 + 可演进服务化**

---

## 2. 第一阶段总体架构

```text
[Vue Portal]      [Vue Admin]
      \              /
       \            /
        ----[Nginx / Gateway]----
                 |
           [Spring Boot App]
                 |
   -----------------------------------------
   |       |        |       |      |       |
 [Auth] [User] [Article] [Comment] [Admin] [Stats]
                 |
        -------------------
        |        |        |
      MySQL    Redis   Kafka Producer
                          |
               ------------------------
               |                      |
       [Search Consumer]     [Notify/Stats Consumer]
               |                      |
        Elasticsearch              MySQL/Redis
```

### 关键点说明
- 主应用先集中开发，减少复杂度
- 发布文章时主链路写 MySQL
- 发布成功后通过 Kafka 驱动异步副作用
- 搜索与通知逻辑通过消费者处理，天然具备后续拆服务的空间

## 3. 模块划分

## 3.1 auth 模块
职责：
- 注册、登录、退出登录
- JWT 颁发与刷新
- 权限校验
- 登录日志

## 3.2 user 模块
职责：
- 用户信息
- 关注关系
- 个人主页
- 作者信息展示

## 3.3 article 模块
职责：
- 文章新增、编辑、草稿、发布、下线、删除
- 分类、标签
- 文章详情
- 热门文章
- 文章版本

## 3.4 comment 模块
职责：
- 评论发布
- 回复评论
- 评论树查询
- 评论审核
- 评论删除

## 3.5 search 模块
职责：
- Elasticsearch 索引写入
- 搜索查询
- 搜索高亮
- 聚合与排序
- 索引重建

## 3.6 notification 模块
职责：
- 关注作者后文章发布通知

## 3.7 stats 模块
职责：
- PV/UV

职责：
- 评论审核

## 4. 核心链路

## 4.1 文章发布链路

```text
作者发布文章
   -> 参数校验
   -> 保存文章元数据 MySQL
   -> 保存正文 MySQL
   -> 更新标签关系
   -> 记录 outbox/event（可选）
   -> 提交事务
   -> 发送 ArticlePublished 事件到 Kafka
   -> Consumer 消费事件
      -> 同步 ES 索引
      -> 给关注者生成通知
      -> 刷新热榜/统计缓存
```

### 这样设计的好处
- 主请求只做必须事务，响应更快
- 副作用统一异步
- 后续可直接把搜索与通知拆出去

---

## 4.2 文章读取链路

```text
访问文章详情
   -> 先查 Redis 详情缓存
   -> 未命中回源 MySQL
   -> 回填 Redis
   -> 异步累加阅读量 PV
   -> 周期性/异步刷新统计
```

### 设计重点
- 详情缓存设置 TTL
- 更新文章后要删除详情缓存
- 防止热点文章缓存击穿，可用互斥锁/逻辑过期

---

## 4.3 搜索链路

```text
用户输入关键词
   -> search-service / search 模块查询 ES
   -> 关键词匹配标题、摘要、正文、标签
   -> 返回高亮片段与分页信息
   -> 用户点击文章详情
   -> 详情页走缓存链路
```

### 搜索能力要求
- 标题权重 > 标签权重 > 正文权重
- 高亮关键词
- 支持分类/标签过滤
- 支持最新/最热排序

---

## 4.4 评论链路

```text
用户发表评论
   -> 鉴权
   -> 敏感词校验（可同步或异步）
   -> 保存评论到 MySQL
   -> 如果需要审核，则状态为 PENDING
   -> 评论成功发送事件
      -> 通知作者 / 被回复人
      -> 更新评论计数
```

### 注意
评论属于核心业务数据，不建议先进内存队列再落库。应先可靠写库，再异步处理副作用。

---

## 5. 数据一致性策略

## 5.1 MySQL 与 Redis
- 新增/更新文章后删除详情缓存
- 列表缓存按分类/标签维度删除或短 TTL
- 热榜缓存由定时任务或事件刷新

## 5.2 MySQL 与 Elasticsearch
- 通过 Kafka 事件同步
- 消费端做幂等
- 支持全量重建索引任务

## 5.3 业务数据与消息投递
推荐两种方案：

### 简化方案（第一阶段可用）
事务提交后发送 Kafka 消息，失败写本地日志并补偿任务重发

### 增强方案（第二阶段推荐）
使用 Outbox Pattern：
- 在事务中写业务表 + outbox_event 表
- 异步扫描 outbox_event 表推送 Kafka
- 推送成功后标记已发送

## 6. 缓存设计

### 6.1 文章详情缓存
key：
- `article:detail:{articleId}`

### 6.2 热门文章缓存
key：
- `article:hot:top10`
- `article:hot:category:{categoryId}`

### 6.3 文章列表缓存
key：
- `article:list:{page}:{size}:{category}:{tag}:{sort}`

### 6.4 PV 计数
key：
- `article:pv:{articleId}`

### 6.5 限流
key：
- `rate:comment:{userId}`
- `rate:login:{ip}`

## 7. 第二阶段服务化拆分建议

当第一阶段完成后，可按以下方式拆分：

### 7.1 search-service
负责：
- Kafka 消费
- ES 索引同步
- 搜索查询 API

### 7.2 notification-service
负责：
- Kafka 消费
- 站内信生成
- 邮件/订阅消息推送

### 7.3 stats-service
负责：
- 行为日志汇总
- 热榜计算
- 仪表盘统计

此时仍可先使用 HTTP 或消息通信，不必强行上 Dubbo。

---

## 8. 第三阶段 Dubbo 引入点

如果你确实想展示 Dubbo，可以在阶段三这样引入：

- article-service 提供文章基础查询接口
- search-service 调用文章接口补充展示信息
- notification-service 调用 user-service 获取订阅关系
- stats-service 提供热榜查询 RPC

这样 Dubbo 的出现就有了明确理由，而不是“为了用而用”。

---

## 9. 架构结论

最推荐的说法是：

> 我先采用模块化单体完成博客的核心业务闭环，再通过 Kafka 驱动搜索同步、通知发送、热度刷新，保证主链路轻量；当系统边界清晰、异步链路稳定后，再逐步拆出搜索和通知服务，并预留 Dubbo 服务治理的演进空间。
