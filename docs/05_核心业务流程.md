# 05 核心业务流程

> 本文描述当前代码实现的真实链路。所有事件分发均为进程内（Spring `ApplicationEventPublisher`）。

## 1. 文章创建与发布

### 1.1 创建草稿

```text
POST /api/article/create
   -> ArticleServiceImpl.createArticle
      -> 校验当前用户
      -> 校验分类存在
      -> 插入 pb_article (status=DRAFT, view_count=0, like_count=0, comment_count=0, collect_count=0, is_top=0, is_featured=0)
      -> 插入 pb_article_content (content + htmlContent + word_count)
      -> 写入 pb_article_tag 关联
      -> 维护 tag.article_count +1
      -> return getArticleDetail(id)
```

### 1.2 发布

```text
POST /api/article/publish
   -> ArticleServiceImpl.publishArticle
      -> 校验当前用户
      -> 校验文章存在 + 校验作者本人
      -> pb_article.status = PUBLISHED
      -> pb_article.published_at = now
      -> 可能更新 is_featured / is_top
      -> ArticleEventProducer.sendArticleEvent(ArticleEvent{eventType="PUBLISHED", ...})
           -> SearchServiceImpl.onArticleEvent -> 同步 ES 索引
      -> 失效文章详情缓存
      -> user.article_count +1
      -> category.article_count +1
```

### 1.3 异步副作用
- 搜索同步（通过 `ArticleEvent` 监听）
- 通知（**当前实现未监听 ArticleEvent**，等后续接入）

---

## 2. 文章更新流程

```text
PUT /api/article/update
   -> ArticleServiceImpl.updateArticle
      -> 校验作者
      -> 更新 pb_article (title/summary/cover_url/category_id)
      -> 更新 pb_article_content (content + html_content + word_count)
      -> 重建 pb_article_tag 关联
      -> 维护每个 tag 的 article_count
      -> 失效详情缓存
      -> return getArticleDetail(id)
```

> 当前实现**不会主动发 ArticleEvent 给搜索**。若需要让 ES 同步更新，需要在更新后追加 `eventProducer.sendArticleEvent(...)`。

---

## 3. 文章下线 / 删除

```text
POST  /api/article/offline/{id}    -> pb_article.status = OFFLINE
                                    -> ArticleEvent(OFFLINE) -> 删除 ES 索引
                                    -> 失效详情缓存

DELETE /api/article/{id}           -> 删除 pb_article / pb_article_content / pb_article_tag
                                    -> ArticleEvent(DELETED) -> 删除 ES 索引
                                    -> 失效详情缓存
                                    -> user.article_count -1
                                    -> category.article_count -1
```

---

## 4. 文章详情访问

```text
GET /api/article/public/{id}
   -> ArticleCacheManager.getArticleDetail(id)
      -> 命中：incrementPv + return
      -> 未命中：
         -> 查 MySQL
         -> 校验 status == PUBLISHED
         -> buildDetailVO（含作者、分类、标签、统计）
         -> cacheArticleDetail(id, vo)  TTL 30 分钟
         -> incrementPv
   -> return VO
```

### 关键点
- 详情缓存不能永久保留，TTL 30 分钟
- 已删/已下架文章不会进入缓存（接口抛 `ARTICLE_NOT_FOUND`）
- PV 只在 Redis 计数，不实时刷 MySQL（`pb_article.view_count` 由数据库初始值 + 后续定时任务维护）

---

## 5. 评论发布

```text
POST /api/comment/create
   -> CommentServiceImpl.createComment
      -> 校验当前用户
      -> 校验文章存在且已发布
      -> (可选) 校验父评论存在
      -> 插入 pb_comment (status=APPROVED, parent_id=0 或具体 ID)
      -> pb_article.comment_count +1
      -> publishEvent(CommentCreatedEvent)
           -> NotificationEventListener.onCommentCreated
              -> 给文章作者 / 被回复人发通知
```

> 当前实现**不做预审核**，评论直接进入 APPROVED。仍然存在 `status=PENDING` 状态用于将来扩展。

---

## 6. 评论审核

```text
GET /api/admin/comment/pending?page=1&size=20    -> 列出 status=PENDING 的评论
POST /api/admin/comment/audit/{id}?approve=true -> 通过 (status=APPROVED)
POST /api/admin/comment/audit/{id}?approve=false -> 拒绝 (status=REJECTED)
DELETE /api/admin/comment/{id}                   -> 直接删除
```

---

## 7. 搜索

```text
GET /api/search?keyword=...&categoryId=...&tagId=...&sortBy=...&sortOrder=...
   -> SearchServiceImpl.search
      -> ensureIndexExists
      -> 构造 BoolQuery：
         must:    title(3.0) / summary(2.0) / tagNames(2.5) / content(1.0)
         filter:  categoryId / tagId / status=PUBLISHED
      -> 高亮 title / summary / content
      -> sort: relevance / viewCount / likeCount / publishedAt
      -> esClient.search(...)
      -> 返回 SearchResult(hits, total, page, tookMs)
```

`POST /api/search/index/rebuild` 全量重建索引。

---

## 8. 热榜刷新

### 8.1 实时累加

```text
StatsPvEvent      -> increasePv + addHotScore(articleId, +1)
StatsLikeArticleEvent -> addHotScore(articleId, +10)
```

### 8.2 定时兜底

```text
@Scheduled(fixedRate = 300000)   // 5 分钟
   -> refreshHotArticles
      -> list(status=PUBLISHED)
      -> 清空 ZSet
      -> score = view_count + like_count*10 + comment_count*5
      -> 写 ZSet
```

### 8.3 接口
- `GET /api/stats/hot?days=7&limit=10` - 返回热榜
- `GET /api/stats/author/{authorId}?limit=10` - 作者热度

## 9. 通知

```text
CommentCreatedEvent -> onCommentCreated
   -> 顶级评论：通知 article_author_id
   -> 回复评论：通知 reply_to_uid
   -> 跳过自己评论自己

FollowCreatedEvent   -> onFollow
   -> 通知 following_id

StatsLikeArticleEvent -> onStatsLike
   -> 通知 article_author_id
   -> 自己给自己点赞跳过
```

## 10. 登录流程

```text
POST /api/auth/login  {username, password, captchaKey?, captchaCode?}
   -> AuthServiceImpl.login
      -> (可选) 校验图形验证码（Redis 5 分钟）
      -> 用户名校验（不存在记失败日志）
      -> BCrypt 校验密码
      -> 校验用户状态正常
      -> 更新 last_login_at
      -> 记登录日志
      -> 生成 accessToken (24h) + refreshToken (7d)
      -> refreshToken 存 Redis
      -> return AuthResponse{accessToken, refreshToken, user, expiresIn}
```

```
POST /api/auth/refresh {refreshToken}
   -> 校验 refreshToken 签名 + type=refresh
   -> 校验用户存在 / 状态正常
   -> 重新颁发 accessToken + refreshToken
```

```
POST /api/auth/logout
   -> 拿到当前 accessToken
   -> 写入 Redis 黑名单 (TTL = accessToken 剩余有效期)
```

## 11. 缓存一致性

### 11.1 文章更新后
- 删除 `pureblog:article:detail:{id}`
- 当前实现不主动删除列表缓存（列表走 DB 或 Redis 短 TTL）

### 11.2 文章删除 / 下线后
- 删除详情缓存
- ES 文档删除（通过 ArticleEvent 监听）

### 11.3 评论 / 点赞后
- 评论计数会更新 `pb_article.comment_count` / `like_count`
- 详情缓存虽然没失效，但下一次写操作（更新文章）会顺带失效它

### 11.4 用户关注后
- 删除被关注者资料缓存

---

## 12. 索引重建

```text
POST /api/search/index/rebuild
   -> SearchServiceImpl.rebuildAllIndex
      -> createIndex (幂等)
      -> 查所有 status=PUBLISHED 的文章
      -> 逐条 buildDocument + indexArticle
      -> 每条失败不影响其他
```

适用于：
- 首次启动后初始化索引
- 上线后修复索引不一致

---

## 13. 流程设计结论

本项目最该重点讲的不是"有多少功能页面"，而是三条链路：

1. **发布链路** —— 写完事务 → 发 ArticleEvent → 搜索同步
2. **搜索链路** —— 走 ES → 高亮 → 点击走详情缓存
3. **热点读取链路** —— 详情 Redis 缓存 + PV 累加 + 热度 ZSet

只要这三条链路完整、稳定、可解释，这个项目就足够强。
